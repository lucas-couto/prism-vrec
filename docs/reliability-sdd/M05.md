## Implementation

Files: `src/utils/memory.py`, `src/steps/train.py`, `src/utils/parallel.py`, `src/steps/evaluate.py` (lazy opt-in only), `src/folds/runner.py` (lazy opt-in only).

- **Budget**: `resolve_host_budget(config)` → `HostBudget(limit_bytes, source, available_bytes)` with source `config | cgroup_v2 | cgroup_v1 | host | fallback`; the fallback is 4 GiB, never `None`/unlimited.
- **Ledger** (`estimate_job_bytes`): worker base (1.5 GiB) + feature payload from `.npy` headers (`feature_payload_bytes` sums a sidecar's components; lazy jobs are charged two 8192-row staging blocks instead of the catalogue) + `estimate_model_state_bytes` (`(n_users + n_items + visual_dim) × d × 16 B`: weight, gradient, two Adam moments) + interaction dicts (CSV size × 40) + `host_ranking_bytes(n_items)`.
- **Admission** (`plan_training_admission`): per job, residency is decided by `resources.feature_residency` (`auto` → lazy when the dense payload exceeds half the usable budget); a job whose total exceeds `budget − headroom` is refused with a reason naming every ledger term; the pool is sized by `admit_workers(heaviest admitted estimate, hard_cap=requested or CPU quota, max_workers)` so the aggregate commitment fits. `_run_grid` records refused jobs as `failed` outcomes (`error_type=AdmissionRefused`, 0 attempts) without launching them, runs the admitted ones, and E02's reconciliation raises `TrainingJobsFailedError` — the refused job is never launched repeatedly and the run is non-success. `TrainingOrchestrator(admission=plan)` clamps a pinned worker count to the admitted one (warning) and raises `AdmissionError` when nothing is admitted (the M06 enforcement, landed here so the wiring is enforced from the start).
- **Lazy wiring** at the four M01 call sites behind the opt-in: worker (`job.lazy_features`, cache key distinguishes the two forms), Optuna/replay/fixed trials and evaluate/folds through `lazy_features_for(config, path)`.

**Recorded choice — default stays `dense`.** `tests/test_training_admission.py::TestLazyPathIsNumericallyIdentical` trains VBPR through `train_single_run` on a pooled `.npy` and on a learned-alignment sidecar, dense vs lazy, and the returned selection value and every promoted weight tensor are bit-identical (`torch.equal`); M02 proved the same for every visual recommender at the model level; the full dense-path suite passes. The default nevertheless remains today's resident matrices because the lazy path's page-cache residency and throughput on production catalogues are unmeasured (V02); `feature_residency: auto` is the recommended setting for the constrained profile once the key names are approved.

Scientific invariants: none touched (the ledger and admission change only whether/how many jobs run, and the lazy path is bit-identical by test).
