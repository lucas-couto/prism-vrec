## Defect and reproduction

Confirmed against the current checkout by `tests/test_extraction_resume.py` before the patch (14 of 18 failed):

- Completed-but-unfinalised part file (`rows_done == N`, `last_batch_index == -1`, crash before `save` renames): resume started at batch zero with `row == N` and crashed with `ValueError: could not broadcast input array from shape (4,4) into shape (0,4)` (`base.py:539`). The artifact could never be finalised without deleting the checkpoint by hand.
- Batch-size change on resume: `start_batch = last_batch_index + 1` under the new batch size mapped to a different row offset, shifting rows (`shape (3,4) into shape (2,4)` errors or silently misaligned content).
- No identity validation: a part file produced from a reversed input order or by other weights was resumed as if compatible (`test_changed_input_order_restarts_clean`, `test_changed_recipe_restarts_clean`, `test_changed_dtype_restarts_clean` failed on content).
- Progress JSON with missing keys raised `KeyError: 'last_batch_index'` instead of being handled.
- Legacy v1 sidecars were trusted blindly (`test_legacy_progress_without_identity_is_not_trusted` failed on poisoned rows).

Three initial failures were fixture bugs of mine (12 items / batch 4 is exactly 3 batches, so "die at batch 3" never fired); fixed to 15/16-item catalogues so the interruption is genuine.

## Implementation

Changed files:

- `src/extractors/resume.py` (new private module): `StreamIdentity` (n_total, on-disk dtype, ordered-input digest from `dataset.item_ids`, extraction-recipe digest over `extractor.metadata()` + kind + dtype + `component_grid`, dataloader batch size), `progress_payload` (schema v2: adds `schema_version`, `batch_size`, `input_digest`, `recipe_digest`, `dtype`, `shape`, `complete`; keeps `last_batch_index`, `rows_done`, `n_total`, `item_ids`), `resume_state` (validates JSON/schema/keys/ranges, identity, part-file shape and dtype; `rows_done == n_total` returns a `complete` point; otherwise rewinds `rows_done` to the last boundary of the *current* batch size and resumes from that row offset; anything unverifiable restarts from row 0 with an explicit warning naming the reason).
- `src/extractors/base.py`: `_resume_state` removed (replaced by `resume.resume_state`); `_extract_streaming` builds the identity, skips the batch loop when the point is complete, checks every block fits (`_check_block_fits`: trailing shape and row bound), refuses to write the completion marker unless exactly `n_total` rows/ids were produced, and writes progress only after `memmap.flush()` (unchanged order, now documented as the durable-prefix rule).
- `tests/test_component_streaming.py`: `_IdDataset` exposes `item_ids` (2 lines) so the pre-existing resume tests exercise the identity-verified path rather than a restart.

Algorithm choices: rewinding to the last batch boundary (instead of failing) satisfies "work from row offsets with identical row content" because every built-in extractor is a per-item deterministic function in eval mode; the recomputed rows are overwritten with identical values. Datasets without `item_ids` (identity unknown) and dataloaders without a fixed `batch_size` cannot be validated and restart explicitly. Scientific invariants: none touched (extraction outputs, dtype, recipes unchanged).

## Limits and next handoff

- Existing `.progress.json` files on disk (schema v1) will not be resumed: the next extract run restarts those cells from row 0 with a warning. Finished artifacts (`.npy` already renamed) are unaffected.
- The recipe digest includes `repr(transform)`; a library upgrade that changes the repr string invalidates in-flight part files (restart, never silent reuse). It cannot detect a weights file changed under the same `weights_id`.
- Input identity relies on `dataset.item_ids` (`ImageDataset` provides it after S01); plugin datasets without it always restart.
- `_iter_batches` still iterates (and decodes images for) the skipped batches before `start_batch`; unchanged, out of scope.
- Not measured: real catalogues, GPU, cross-filesystem finalisation.
