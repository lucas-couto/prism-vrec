## Defect and reproduction

F14 re-validated against the current checkout; every part confirmed, plus two adjacent findings.

1. **Dockerfile installed from ranges, not the lock** (confirmed). `Dockerfile` copied only `pyproject.toml` and ran `pip install -e ".[telemetry]"`; `uv.lock` was never read. Evidence: the running image `prism-vrec-shell:latest` (id `sha256:b0054c25d312...`, built 2026-08-21) differs from `uv.lock` on 20 packages, among them **timm 1.0.28 (image) vs 1.0.27 (lock)** — the only numerical library affected; all 20 lie inside pyproject's ranges. Full diff in `docs/environment.md` §3.
2. **CI torch constraint contradicted the package** (confirmed). `ci.yml` installed `torch>=2.1.0,<2.6` / `torchvision>=0.16.0,<0.21` from the CPU index in three jobs, while pyproject requires `torch>=2.8,<2.9` / `torchvision>=0.23,<0.24`; the subsequent `pip install -e .` would then replace them with the CUDA torch 2.8 from PyPI.
3. **`uv.lock` is stale relative to `pyproject.toml`** (new, adjacent). `uv lock --check` fails: the lock's `prism-vrec` metadata is 2.5.0 (commit 4050469, #22) and lacks the `telemetry` extra added in 2.6.0 (#23). `uv lock --dry-run` reports exactly three changes: `prism-vrec 2.5.0 -> (dynamic)`, `psutil 7.2.2 -> 6.1.1`, `nvidia-ml-py 13.610.43 -> 12.575.51` (the extra's `<7.0` / `<13.0` ceilings are tighter than codecarbon's). **Not regenerated**: the brief allows regeneration only if the result equals the image, which is impossible (the image already differs from the lock, item 1); a regeneration is a reviewed dependency operation.
4. **The running image predates its own Dockerfile** (new, adjacent). It has neither `psutil` nor `nvidia-ml-py`: telemetry has been running on the `nvidia-smi` + `getrusage` fallbacks and the manifest's `ram_total_gb` is `null`. `pytest` (9.1.1, lock says 8.4.2) and `ruff` live in the host-mounted `.cache/.local` user site, not in the image.
5. **Build context leaked `.cache/` (2.0 GB) and `.env`** (new). Neither was in `.dockerignore`; `COPY . .` baked them into the image.

Reproduction is `tests/test_environment_lock.py` (before the patch: `2 failed, 4 passed, 1 xfailed`; the failures are `test_dockerfile_installs_from_the_lock_not_from_ranges` — "uv.lock is not copied" — and `test_ci_installs_torch_inside_the_package_range_at_the_locked_version` — "torch<2.6,>=2.1.0: neither pyproject's <2.9,>=2.8 nor ==2.8.0").

## Implementation

Changed files (all inside V01 ownership):

- `Dockerfile` — dependency layer now `COPY pyproject.toml uv.lock`, `pip install --upgrade pip "uv==0.9.5"`, `uv export --frozen --no-dev --no-emit-project`, `pip install --no-deps --require-hashes -r`, `pip install --no-deps --no-build-isolation -e .`, `pip check`. The `telemetry` extra is installed in a separate `RUN` from the same ranges as pyproject (`psutil>=5.9,<7.0`, `nvidia-ml-py>=12.535,<13.0`) because the lock does not carry it (item 3); this is the only range-resolved runtime content left. CPU/CUDA selection is unchanged (PyPI torch wheel per platform) and documented in the file header and `docs/environment.md` §4. uv is kept in the image so `uv lock` can run from the `shell` service on this Python-less host.
- `.github/workflows/ci.yml` — the three torch install lines pin `torch==2.8.0` / `torchvision==0.23.0` (lock versions, inside pyproject's ranges) from the CPU index; comment explains that CI is a CPU-test environment (`2.8.0+cpu`, `torch_cuda_available: false`).
- `.dockerignore` — adds `.cache/` and `.env`.
- `docs/environment.md` (new) — image digest, versions, full `pip freeze`, mismatch table, build recipe, CPU-vs-GPU metadata distinction, regeneration commands.
- `tests/test_environment_lock.py` (new) — 7 tests, `tomllib` + `packaging` + `yaml` (all already installed): every runtime dependency locked inside its range; numerical packages pinned; lock `requires-dist` parity with pyproject (**strict `xfail`** documenting item 3 — it flips to an error the day the lock is regenerated, prompting removal of the marker); Dockerfile copies the lock, exports frozen, requires hashes, installs no extra from ranges; Dockerfile base Python inside `requires-python`; CI numerical pins equal the lock version and lie inside pyproject's range; CI ruff pin equals the lock.

Scientific invariants: none touched. No dependency version changed; the next image build installs timm 1.0.27 instead of 1.0.28 because the lock says so — a consequence of enforcing the existing lock, not an upgrade. Whether that changes any extracted feature is a Q07 question for the integrator: timm's patch changelog between 1.0.27 and 1.0.28 should be read before pre-rebuild and post-rebuild feature artifacts are treated as identical.
