## Defect and reproduction

Confirmed behaviour on the pre-patch `src/utils/parallel.py` (audit F04, requirements Q11/Q12):

1. **Sequential path never retried OOM and could lose the result entirely.** `_run_sequential` drained with `while not result_queue.empty()` on an `mp.Queue`; the feeder thread had not flushed when the check ran. Reproduction (`scratchpad/repro_e01_before.py`, synthetic dataset + `train_single_run` monkeypatched to raise `torch.cuda.OutOfMemoryError`, real worker loop): `train_single_run attempts = 1`, `results = []` — one submitted job, one attempt, **zero** outcomes returned to the caller.
2. **Parallel path: a worker that died before publishing left its job silently absent.** The loop counted `completed` messages against `total`; a dead worker produced no message, so the loop only ended when every worker had exited ("All workers exited.") and the job never appeared in `results`. Duplicate messages incremented `completed` and could end the loop with another job unaccounted.
3. **OOM retry count differed between paths.** Parallel: OOM -> deferred to a sequential pass that did not retry again (2 attempts in practice, `MAX_OOM_RETRIES = 2` notwithstanding). Sequential: 1 attempt.

The new regression file `tests/test_parallel_job_outcomes.py` does not import on the old module (`_JobRegistry`, `job_runner` absent), which is why the before-evidence was taken with the scratch script above.

## Implementation

Changed file: `src/utils/parallel.py` only.

- `JobOutcome` (frozen dataclass, C03 as an internal record): `job_id`, `attempt_id` (`<job_id>#<attempt>`), `status` in {`succeeded`, `failed`, `cancelled`}, `attempt_count`, `error_type`, `error_message`, `best_metric`, `identity` (dataset/model/embedding/hyperparams). `to_result()` renders the historical public dict.
- `_JobRegistry`: parent-side ledger. Every submitted job is `open` -> (`retry_pending`)* -> terminal. `record()` applies one worker message and returns `False` for duplicates / unknown ids / messages for already-terminal jobs (logged, never applied). `fail()` and `cancel_open()` create terminal outcomes without a message. OOM handling lives here: `retry_count < MAX_OOM_RETRIES` -> `retry_pending`, otherwise `failed` with `error_type="OutOfMemoryError"`. Only the `oom` message status (emitted solely for `torch.cuda.OutOfMemoryError`) can reach that branch; any other exception is `failed` after one attempt.
- Worker loop split: `_worker_fn` (queue loop + publication) / `_run_one_job` (one attempt -> one message, carrying `attempt` and `error_type`) / `_WorkerContext` (config, `CheckpointManager`, the two `SingleSlotCache`s, VRAM probe via `cap_process_vram`, unchanged training call). `_WorkerContext` is built lazily on the first real job so an injected `job_runner` never touches config or checkpoints.
- Last assignment: a spawn-context `ctx.Array("i", n_workers)`; the worker writes `job.submit_index` before running and `-1` after publishing. The parent, on every poll timeout, reaps workers that are no longer alive: an assigned job with no terminal outcome becomes `failed` with `error_type="WorkerExit"` and the exit code in the message. Shared memory is written synchronously, so a SIGKILL between `queue.get` and `queue.put` cannot lose the assignment the way a queued "started" message could.
- Queue emptiness is no longer consulted. The sequential path uses thread `queue.Queue`s (in-process worker, no feeder thread) and reconciles the batch against the registry; the parallel loop runs while `registry.open_ids()` is non-empty, drains with a bounded `get(timeout=_RESULT_POLL_S)`, and when no worker is alive drains once more, reaps, and cancels whatever never started (`error_type="PoolExited"`).
- Retry limit is shared: OOM retries collected by the pool are handed to `_run_sequential_into`, which loops until `take_retries()` is empty. Both paths therefore execute a job at most `MAX_OOM_RETRIES + 1 = 3` times, and the ranking-budget shrink per retry (`_OOM_SHRINK_PER_RETRY ** retry_count`) is unchanged.

Scientific invariants: none touched. No change to loss, candidates, tie policy, selection cadence, the checkpoint layout, `_RANKING_VRAM_SHARE`, `cap_process_vram` call sites (AST test still passes) or the single-slot caches.
